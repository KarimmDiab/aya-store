# مراجعة مشروع Aya Store

مراجعة توثيقية فقط — لا تمثل إصلاحًا أو اختبار قبول شاملًا. لم تُغيّر بيانات قاعدة البيانات أو منطق البرنامج في هذه المراجعة.

## 1. بيانات النسخة

- **المستودع:** https://github.com/KarimmDiab/aya-store.git
- **الفرع:** `main`
- **آخر commit تمت مراجعته:** `5cea8614ada4746d88751e870c7c8ecdb718741b` — `Initial safe commit for Aya Store`، بتاريخ 5 نوفمبر 2026.
- **Git عند بدء المراجعة:** نظيف ومتزامن مع `origin/main`؛ لا توجد تغييرات محلية غير مرفوعة. إنشاء هذا التقرير يضيف ملفًا محليًا جديدًا غير مرفوع.
- **تاريخ المراجعة:** 5 نوفمبر 2026، توقيت القاهرة.
- لم يُنشأ commit ولم يُنفذ push في مهمة المراجعة.

### الوحدات الموجودة في الكود

- المصادقة وصفحات تسجيل الدخول وكلمات المرور، وإنشاء المستخدمين والأدوار والصلاحيات.
- المستخدمون والفروع والمخازن.
- تصنيفات المنتجات والمنتجات والكميات والأسعار.
- فواتير الشراء وتفاصيلها، الموردون، والمدفوعات المستحقة للموردين.
- فواتير البيع وتفاصيلها، العملاء، البيع الآجل، وتحصيل دفعات العملاء.
- بنود المصروفات وتفاصيلها ومرفقاتها.
- تقارير إجمالي المبيعات والمبيعات حسب المنتج والعميل والمستخدم، مع تصدير Excel ضمن الاعتماديات.
- واجهات Blade، وأصول واجهة ثابتة، وVite/Vue للموارد المعرّفة في `vite.config.js`.

وجود المسارات والواجهات يثبت وجود الكود فقط، ولا يثبت أن تدفقات البيع والشراء والدفع تعمل end-to-end.

### التشغيل والاعتماديات

المتطلبات الأساسية: PHP 8.1 أو أحدث مع إضافات Laravel وPDO MySQL المناسبة، Composer، MySQL، وNode/npm عند بناء أصول Vite. خطوات Laravel المعتادة هي تثبيت Composer، نسخ `.env.example` إلى `.env` محليًا، إعداد مفتاح التطبيق واتصال قاعدة البيانات، ثم تشغيل `php artisan serve`؛ ولأصول Vite استخدام `npm ci` ثم `npm run dev` أو `npm run build`.

**عائق إعداد مهم:** المستودع يحتوي migrations Laravel الافتراضية وSpatie فقط، ولا يحتوي migrations لجداول العمل الأساسية مثل المنتجات والفواتير والعملاء والموردين والمخازن. ملفات SQL مستثناة من Git. لذلك لا تكفي خطوات Laravel المعتادة لإنشاء نسخة جديدة قابلة للتشغيل، ويجب تحديد مصدر schema موثوق قبل اعتماد تعليمات تشغيل نهائية. لم أشغّل migrations أو seeders ولم أتصل بقاعدة بيانات.

## 6. نطاق تسليم 8 نوفمبر 2026

### الضروري للتسليم

1. إغلاق SEC-01 وSEC-02 قبل إتاحة النظام على شبكة يستخدمها أكثر من شخص.
2. تثبيت قواعد الحساب والمخزون والمدفوعات، ثم تنفيذ SALE-01 وSTK-01 وPAY-01 وINV-01.
3. حسم ما إذا كان التسليم يتضمن تثبيتًا جديدًا؛ إن كان نعم، SET-01 وSET-02 وQA-01 شروط لازمة.
4. اختبار عملي على قاعدة اختبار وبحساب مالك وحساب موظف، لا على بيانات العملاء الفعلية.

يمكن تأجيل RPT-01، كما يمكن تأجيل API-01 فقط إذا تأكد أن API غير مستخدم. لا أوصي بتأجيل إغلاق الوصول غير المحمي أو قواعد الأموال والمخزون.

### واقعية الموعد

من 5 إلى 8 نوفمبر ثلاثة أيام تقويمية. إذا توفر مطور واحد بمعدل 6–8 ساعات تركيز يوميًا، فالمتاح تقريبيًا 18–24 ساعة. تقدير مهام P0 وعمليات البيع/المخزون/المدفوعات والاختبارات يتجاوز ذلك غالبًا، وتوفير schema تثبيت جديد قد يضيف 6–10 ساعات. لذلك **التسليم الكامل غير مضمون وغير واقعي ضمن 18–24 ساعة** دون تقليص نطاق واضح؛ قد يكون تسليم شريحة حرجة ممكنًا بعد قرارات سريعة، لكن يجب عدم تقديمه كضمان قبل تحقق عملي.

### قرارات ومعلومات مطلوبة من أحمد عادل

- ما العمليات التي يسمح بها للموظف: البيع، تعديل/إلغاء الفواتير، الخصم، التحصيل، تغيير سعر المنتج، المخزون، التقارير، إدارة المستخدمين؟
- هل تقبل الفاتورة دفعة جزئية؟ ما حد الخصم؟ وكيف تسجل الدفعات الزائدة، رد الأموال، والمرتجعات؟
- هل المطلوب تثبيت من الصفر ضمن موعد 8 نوفمبر، أم استخدام قاعدة المعرض الحالية؟ ما schema المعتمد وكيف تتم ترقية بياناتها؟
- هل endpoint إدارة الصلاحيات عبر API مستخدم من تطبيق آخر؟
- كم ساعة متاحة للمراجعة والقبول العملي قبل الموعد، ومن يعتمد أرصدة البداية؟
- يجب إبطال/تغيير كلمة مرور حساب seed الثابت قبل أي تشغيل حقيقي؛ لم تُعرض قيمتها في هذا التقرير.

## 7. ملخص تسليم لـChatGPT

Aya Store على Laravel 10 يعمل وفق وصف المالك، لكن المراجعة الحالية كانت ساكنة ومحدودة: suite فيها اختبار Unit واحد ناجح واختبار الصفحة فشل لغياب `APP_KEY`، و`route:list` يفشل بسبب namespace API خاطئ. أهم ثلاث أولويات هي حماية مسارات المستخدمين والعملاء والفواتير، إزالة تسريب كلمة المرور إلى السجل وحساب seed الثابت، ثم ضبط حساب الفواتير والمخزون والمدفوعات من الخادم مع اختبارات. كذلك لا توجد migrations لجداول المجال في المستودع، لذا التثبيت الجديد غير مثبت. العائق الرئيسي هو غياب مصفوفة صلاحيات الموظف وسياسة الدفع/المرتجعات ومصدر schema معتمد. الخطوة التالية المقترحة: حسم هذه القرارات مع أحمد عادل، ثم تحويل SEC-01 وSEC-02 وSET-01 وSALE-01 وSTK-01 وPAY-01 وQA-01 إلى مهام Notion بالمعايير أعلاه. لا تمثل هذه المراجعة إصلاحًا أو وعدًا بموعد التسليم.
